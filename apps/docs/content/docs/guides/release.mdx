Kind UI is pre-release and unpublished. `@kind-ui/charts` is an unpublished `0.1.0` candidate; CI performs checks and publishing remains disabled. The docs preview is a separate private Site. A Site URL or generated agent endpoint does not establish anonymous access or a public npm package.

The current docs package source is <PackageSource />. The served [provenance JSON](/package-provenance.json) records the actual installed source commit, SHA-256 and npm integrity. The [Line setup files](/examples/line/README.md) and [pinned artifact](/examples/package/kind-ui-charts-0.1.0.tgz) retain this exact package. The pin includes the merged chart APIs and fixes from validated source `d66ad717eaa0220b83b60de9420c94b65d67118c`; use the validated bytes rather than substituting another build. Check provenance when reproducing a result; `0.1.0` alone does not identify validated bytes. Glass is paused and unmerged.

## Preparing a local candidate

From an installed source checkout, `npm pack --workspace @kind-ui/charts` runs a guard that removes stale output, rebuilds and checks the runtime modules, declarations, CSS, license and README. Do not use `--ignore-scripts` for candidate preparation.

`npm run pack:artifact` runs the isolated consumer gate and, after success, retains the exact tested `artifacts/package/kind-ui-charts-0.1.0.tgz` with `validated-artifact.json`. That metadata includes filename, SHA-256 and npm integrity. Rerunning removes the previous candidate. Compare the checksum before a handoff; any source, manifest or version change requires a newly prepared and tested artifact.

These local commands do not publish. The package gate proves ESM imports and strict NodeNext/Bundler declaration resolution through a packed consumer at pinned peers. It does not establish CommonJS, SSR hydration, all framework/browser versions or release authorization. Run the required aggregate checks as well before proposing release readiness.

## Before the first public release

The owner must explicitly decide the package set, supported environments, namespace ownership, security-reporting route and release authorization. Release tooling belongs in a separate reviewed setup change. Until then, document compatibility and user-visible changes in the PR rather than maintaining fictional release notes.

The intended future policy is semantic versioning per independently versioned package. After release tooling is adopted, user-facing package changes need a reviewed changeset and compatibility decision, including the pre-1.0 breaking-change policy. Documentation, CI and development-only changes need no package release. Passing CI does not authorize publishing or merging.
